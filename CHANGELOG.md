# Changelog

## 1.4.4

- Init and update apply pending path defaults and review capabilities after a terminal `TASK.md` row closes a readable active timeline. Open tasks and unknown task state still defer these changes.

- Updating 1.2.0 commands refreshes the managed rule contract and adds the required appendix guidance while preserving project commands, the selected skill-pack example and project notes.

- Install and update preserve an existing canonical `TASK.md` when the only proposed change is table formatting.

- During coherent recovery, `next-step` reoffers classification after a failed preflight supersedes the previous artifact. Strict decomposition rechecks resume with the newly classified scope and current review counts.

- The review-cycle guard's `mark_blocked` guidance gives the operator the confirmed task-reset command and the audited command to enable reset when needed.

- Update and rollback accept an operator-closed task with a terminal `TASK.md` row and a readable active timeline. Refusals for open tasks include the confirmed task-reset command and the audited command to enable reset.

- `workflow set` no longer treats the shipped order of optional quality rule scope and changed-file regex lists as a rule change. A config with the default rules keeps no-op settings no-op and asks operator confirmation only for real mutations.

- Translating or renaming a parent in TASK.md after a split no longer blocks child materialization or automatic parent completion when the last child finishes.

- The Navigator routes validation audit problems to the operator before reclassification, including during documentation-delta inspection. After an audited contract readmission, test-first recovery offers a same-path classification refresh only before implementation and only when every classified and live changed path is a recognized test, including rename sources and deletions. Failed or interrupted classification returns to `classify-change`. `workflow set` names the physical line and defect in a malformed audit and preserves it for repair. Confirmed re-approval can recreate a missing audit. Validation inspection retries also track recipe and source identity changes. `workflow set` applies the same optional quality-checks baseline migration as update and identifies automatically written audit fields.

- Review reuse compares authenticated passing task-test artifacts. Declared reports must come from the recorded execution window and match the reviewed paths and SHA-256 digests. Missing or changed evidence requires a fresh FULL review. If a reuse snapshot cannot be written, the gate still publishes the passing suite and disables reuse for that run.
- `gate record-reviewer-delegation-started` accepts optional `--reviewer-provider` and `--reviewer-model`. The launch artifact binds these values for the review receipt and final report.
- Large values in reviewer evidence manifests move to hash-bound files beside the manifest. The review context retains the original values.

- The navigator refreshes handshake and shell-smoke evidence when a TASK_ENTRY reload after the review gate opens a new diagnostics anchor. Classification, compile, required reviews, completion, and navigator effects use the rule-pack artifact selected for the active cycle. Before review starts, the navigator directs agents to reload POST_PREFLIGHT into the TASK_ENTRY artifact when the stages were loaded separately. Recovery commands retain custom preflight and rule-pack paths, and bind remediation resolves relative preflight paths against the repository root.
- When completed quality-checklist answers select trust-boundary cases that need a focused run, the navigator routes that run before recording the checklist. Both instructions name the evaluated preflight and keep each `--selected-case` claim. ACTION_REQUIRED answers still record the finding first and follow the declared-validation route.
- `classify-change` refreshes the POST_PREFLIGHT binding when the current cycle already read the required rules and their hashes, rule set, and review decisions are unchanged. It writes preflight JSON to stdout and binding diagnostics to stderr. `load-rule-pack` holds one artifact lock across event append and publication, and records a digest of the exact redacted stage. Existing stages recorded without a digest need one reload per affected stage.
- An entry beside unfinished tasks names concrete files from the attached plan when available. Authenticated grouped review follow-ups that name protected files request approval at first entry and include the files and flags in the command. Under the Garda self-guard, the navigator directs the operator to maintenance.

- Classification errors now require FULL review instead of falling back to possibly empty task-wide triggers.
- Changing the task's criteria repeats every required review in full, even when a failed review's context is lost or the fix also changes code. Criteria cover its title and notes in the root `TASK.md`, classified intent, operator decisions and linked task-card section, including acceptance criteria in any form. Meaningful spaces, indentation and line structure count; line endings, trailing spaces and other tasks' rows, decisions or cards do not. Review policy comes from `garda-agent-orchestrator/live/config/`; unrelated files with similar names do not trigger a full restart.
- A lost review context is restored from its exact authenticated copy when possible; otherwise the affected review and any declared dependents repeat while other completed reviews stay. After launch, a changed context, prompt, role prompt or rule is restored only when the recorded result proves it was intact. A refused launch preparation never repairs a damaged prompt that an active reviewer may have read. Required-review and review-order checks apply the same restoration rule. Recorded dependency-order failures still require a coherent-cycle restart.
- A lost or damaged reviewer report can be restored from its verified copy. If its findings cannot be proven, the affected review repeats; known findings can still be corrected by the open reviewer. Corrections preserve the original findings, including redacted values, and the first parseable findings after an unparsable report are locked. Without a findings fingerprint, only the original reviewer's live or API continuation may correct the report; if unavailable, Garda offers a full review-evidence-only restart. Correction-only producers still need a fingerprint; reports with one retain all correction transports.
- A lost or changed saved report or receipt can be recovered during an active cycle. The cycle limit counts its recorded verdict, or a failure when the verdict is unknown, and only that review repeats when the task still relies on it. A full task audit checks every committed review snapshot and accepts an exact recorded loss only after its review is repeated.
- Saved reviewer inputs are kept per task and removed on reset or closeout; older shared copies are removed when no other open task needs them. Restoring or syncing unchanged review files no longer interrupts a cycle merely because their timestamps change; changed or missing evidence still blocks the task.
- Recovery from a lost upstream review input recognizes its recorded refusal on Windows network and WSL paths. Completed reviews can be kept through several evidence recoveries when their verified order still applies. A small fix carried through another restart can keep its DELTA review against the tree that reviewer actually saw.
- Corrupt preflight evidence produces a recoverable gate refusal. Garda rebuilds a lost or damaged handshake or shell-smoke file by repeating startup checks before classification, or through `restart-coherent-cycle` afterward, keeping passed reviews. Restart commands preserve the classified task intent even when the task-mode summary differs from the `TASK.md` title. Damaged task history still needs the operator.
- Recording a review result avoids repeated reads of long task histories.

### More languages and build tools

- Garda works with a wider range of languages and build tools. Project discovery, file classification and validation no longer depend on Node.js conventions. Unsupported toolchains receive clear setup guidance. CMake projects get suggested build and `ctest` commands.
- Use your own build and test commands, including focused tests and declared report files. Validation records what actually ran; independent review checks the results before task completion.
- By default, generated build folders stay out of task scopes and reviews. Exclusions are configurable; tracked files always remain visible. Explicit scope requests retain excluded build-output paths in separate authenticated metadata and show the exclusions, so untracked dist files no longer break request binding. Workspace snapshot cache format is now version 9 (version 8 is reserved by the 2.0 branch).
- Validation handles Git line-ending conversion correctly, avoiding false content mismatches on Windows.
- Test reports may be rewritten by the current run. When a report is stale, the error names the directory to clear.
- File names with Cyrillic and other non-ASCII characters, spaces or quotes now work consistently in scopes, line counts and review diffs. Diffs display readable file names.

### Clearer interface and task guidance

- `gate materialize-decomposition-children` creates the child TASK.md rows and the parent provenance note (`Decomposition source: orchestrator`) of an authenticated split, so child rows no longer have to be added by hand. It takes the work packages of a current `split-required` decomposition decision, or, for a scope-budget or review-cycle SPLIT_REQUIRED latch, a root-cause work-package contract passed with `--work-package-contract-path`. Each child gets its objective as title, its profile, its obligations, its validation and an exact `Required reviews:` declaration. The command refuses a partial hand-made set of rows or links, writes nothing then, and is idempotent once the rows exist. A decision split needs both the artifact and its recorded event in the signed part of an intact task timeline; an unsigned legacy-prefix event does not count. The command always checks Git against the parent preflight the decision recorded and refuses while parent implementation WIP is not suspended, also when the parent was edited again after an earlier capture, because child links skip the suspension. It reads TASK.md inside the repository with a size bound, checks eligibility and writes under one queue lock hold, and on a failed evidence write restores only its own queue change. `next-step` offers it at the split route while no child row exists; when the split leaves no implementation WIP, the command is offered directly instead of behind `--execute-effects`. Parent edits made after a suspended capture get a guarded recapture effect that keeps the earlier capture, so the route does not dead-end. The parent still becomes DECOMPOSED through the existing `next-step` transition and its unchanged checks.

- The guarded decomposition decision is no longer a formal step (T-212). `record-strict-decomposition-decision` reads the TASK.md notes of the task and the task cards they reference (`Card: <path>.md` or a linked card). When they plan sub-cards, an `atomic` or `single-cycle` decision must pass one `--plan-disposition "<task id>: <how this row honours it>"` per planned sub-card task, with exact ids and no repeats, unless the card names this row as one of its sub-cards. Only an explicit task-scope statement is a file cap (for example "Scope: at most two files" or "6-file cap"); a number of files in a description, such as what a fixture emits or changes, is not. A decision must pass `--estimated-changed-files` when the task has a plan, the current preflight already changes files, or, before any preflight, the Git workspace already has changes; a decision recorded with a baseline but without an estimate is asked again once the preflight changes files. An estimate over a soft cap needs `--plan-cap-revision` with the justification, which the decision records, prints and puts in its task event; over a cap the card calls hard it can only split, also when a revision lifts a smaller soft cap. The estimate may not be below the files the current preflight already changes. The decision reads that preflight and the review timeline from `--preflight-path` and `--events-root` when given and records which ones it read; `next-step` passes its own non-default paths in the offered command and asks again when the recorded inputs differ from the ones it navigates with. An unreadable preflight counts as missing for both the decision and `next-step`, so the offered command records instead of throwing and `next-step` regenerates the preflight. TASK.md, plain card references and linked task cards are read only as regular files inside the repository with a size bound; a FIFO or device is never opened. Otherwise the gate refuses and prints the `split-required` command with the planned child ids. The decision records the estimate, the detected plan and the changed-file and failed-review counts at decision time. Afterwards `next-step` routes back to `record-strict-decomposition-decision` when the current preflight changes more files than the estimate or the cap, or when failed non-test reviews reach a checkpoint at a third of the review-cycle guard limit counted from the recorded decision; a decision recorded before this change keeps only the checks its own fields allow. The decision is now asked for before implementation (field shop T-014-2): notes that plan sub-cards or a file cap are risk signals before the first preflight, and three or more planned changed files are one at the first preflight while it has no diff yet; before, a task without risky wording got the decision only from the real diff after the code was written. A split recorded after implementation (late split) no longer dead-ends: `next-step` stops generating quality-checklist inputs for the split parent, so the WIP capture does not take and later reject them, and it plans the WIP suspension only when the parent still has implementation WIP. `--estimated-changed-files` is classified as a non-filesystem CLI input. No new operator step is added.

- A linked worktree without a Garda workspace points to the main checkout. Task entry verifies protected files from disk, and the navigator gives the operator inspection, approval, and retry routes.

- A scope expansion can pair exact-file approval with coherent restart. An interrupted restart uses the original protected request. Scope-only entry can reuse current static rules while rerunning the live startup probes.

- Test selection carries authenticated mappings into the new cycle and accepts bounded external plan declarations. Failure follow-ups retain attributed test names, and an ambiguous or in-scope TAP failure stays blocking. A path under `scripts/` activates ops checks only when it matches an ops rule.

- Individual gates print a current next action when there is one executable recovery command. Closeout recovers interrupted test owners before retrying validation. Reviewer-launch publication recovery uses a digest-bound command without repeating the delegation.

- Immediately before task tests, navigation asks agents to reconcile the implemented scope with the linked task card and select current tests. Explicit stale selectors that exclude changed tests are rejected by validation and retained-evidence checks. Linked acceptance criteria are included in reviewer handoffs and mandatory coverage ledgers; a generic follow-up title no longer hides the detailed deliverable.

- Navigation offers a native checklist refresh when valid answers resolve only some required actions. The remaining actions continue to block the task after publication; unchanged or invalid answers do not trigger a refresh.

- A quality-checklist case reference or `--selected-case` claim is accepted only when the cited file contains the case identifier, on every stack. Previously a passing run with the right selector could bind and observe a case cited from the wrong file, even a production file. The refusal names the pair and asks for the declaring file, with the case identifier as written there; the selector may stay the full runner ID. A pending checklist recorded before the update with such a pair asks for corrected answers through `quality-checklist`. Operator-approved recipe targets keep their declared binding.
- Task-test selection no longer refuses a task whose changed files include literal brackets, such as a Next.js `[...nextauth]` route. The glob check now applies only to the selected test targets.
- An operator-approved extra review cycle (`allow_one_more_cycle`) now survives the rework it was approved for. The preflight refresh and the first review-cycle restart after the approval belong to that cycle; a second restart, a failed non-test review, or task completion still ends it. Previously the required preflight or restart ended the approval before any reviewer could launch.
- `next-step` detects the runtime provider only from session markers. A config-path variable such as a global `CODEX_HOME`, or the Claude Code IDE port exported to every integrated terminal, no longer counts, so Claude Code on a machine with Codex installed is no longer offered `--provider "Codex"`. When session markers of several providers are present, or none, the entry command keeps the provider placeholder and asks the agent to pass its own provider; `GARDA_EXECUTION_PROVIDER` stays the explicit override, and the commit guard still treats every marker as an agent shell.
- Before a task has its own current test selection, `next-step` no longer shows the test command left in the shared `workflow-config.json` as this task's command. That command can belong to another active task, so the summary names no command (`command=not selected for this task`, an empty `full_suite_validation.command` in JSON) and the route offers only the task test selection. The shared config is unchanged and the gates keep checking the task-bound selection.
- A failed-review restart no longer widens the remediation scope with planned but unmodified files. `restart-review-cycle` now treats a named file that Git tracks unchanged against HEAD as not changed, as `classify-change` already did, so such files no longer count as added non-test paths, force FULL reviews or block the scope boundary; a real new change still widens it. A lane moved to FULL authenticates against its own current preflight scope instead of the failed lane's DELTA union, and a narrowed or forged FULL scope is still refused. When the persisted remediation authority would make `build-review-context` refuse a lane, `next-step` offers the coherent-cycle restart instead of repeating the failing command.
- Validation output no longer grows without bound. Housekeeping removes a cleaned run folder seven days after finalization (folder age for older manifests), releases failed runs made outside task mode after seven days, and finalizes a run left RUNNING for over a day by dead processes as failed without touching its reports. Runs with a live process, tampered reports and failed runs of an unfinished task are kept as before. A manifest written for another path of the repository, such as a WSL mount, is skipped without a warning.
- When a targeted-test `run-intermediate-command` run timed out for the current preflight, `next-step` no longer offers the same command again unchanged. It offers that command with an explicit `--timeout-ms` (twice the observed run time, rounded up to whole minutes) as an operator-confirmed step and names the `--selected-case` split as the alternative. The default limit is unchanged.
- The `project-memory-impact` route now explains the suggested command when no memory file was edited: `--confirm-updated` records a review without edits, with every candidate as `--skipped-memory-file`, and an outdated candidate must be edited and listed with `--updated-memory-file` instead. It also names the candidate memory lines that mention a changed module (path, file name or its trailing words), so a possibly outdated statement no longer has to be searched by hand. These lines are pointers for review only.
- The final report order now names the exact staging step before the local commit command: `git add --` with only the task's own audited, committable files, never bundle, runtime or unrelated dirty files. Without it `gate human-commit` refused an empty staged scope. Staged-scope tasks get no staging step. The commit command now uses the CLI entry of the checkout (`node bin/garda.js` in a source checkout), like the other navigator commands, instead of always printing the installed-bundle path.
- After a review-cycle restart, `next-step` offers the task's previous test selection for one-step re-confirmation instead of a blank selection command, when that selection still covers every changed test. The selection stays bound to its preflight and target bytes, so a refresh still expires it and it is never reused silently; the offered `workflow set` command carries the previous command, targets and reason and records a new audited selection for the current preflight.
- A fix that continues after `restart-review-cycle` refreshed the preflight for a failed `fix_now` review, before that review runs again, keeps the failed-review restart route (`restart-review-cycle` for the failed lane with the current changed files). Previously, a deferred finding of another review made `next-step` stop at `post-review-source-mutation-guard` with no command. The failure must still authenticate from its receipt in place and the task timeline, and a later task, coherent-cycle or review-gate boundary, reviewer launch, recorded review or another review's phase ends it. When the guard does block, it now always names its routes: an operator-confirmed task intent change through `restart-coherent-cycle` that repeats every review in FULL, or restoring the frozen state (the change goes to the follow-up task) and rerunning `next-step`.
- `next-step` no longer stays on a failed classification whose cause is gone (OP-056). When the latest `PREFLIGHT_FAILED` reports a protected control-plane or workflow-config change and the workflow-config files match the task-mode baseline again, the protected manifest matches and no protected path is in scope, it offers the failed classification again instead of the maintenance route with `doctor` only. The retried gate runs all of its checks. A BLOCKED answer without an agent command (none, only `doctor`, `status`, `why-blocked`, `next-step`, or only operator-only `--confirm` commands) now always gets the read-only `task-reset --reopen --dry-run` preview for the operator, unless the step is the agent's own stated work (editing files, filling the named answers file, running the printed focused check, waiting, or the named capability decision) or an operator decision on the explicit allow-list. The preview never counts as progress for the stand and tests: the walk fails for any route outside those two lists that needed it. The failed classification is re-offered once per content change of the protected files (workflow-config files, the manifest-covered control-plane files and the trusted manifest): each protected `PREFLIGHT_FAILED` records a content witness, so a rollback is seen even when the restore keeps the old file times, a retry that failed while the files were still changed does not block the re-offer after the rollback, and a retry failing on unchanged content is not offered again. A missing or unreadable witness counts as unchanged, and nothing is re-offered when the Git workspace cannot be read. The operator decision of a not-ready final report keeps its marker in the rendered answer, so it is not reported as a dead end.
- A rejected declared validation (`project-validation-evidence`) now says who resolves it. A rejected or cancelled run of an admitted recipe offers the exact `gate run-intermediate-command --recipe-id <id>` fresh run again; a rejected native check routes to the focused run the agent declares; an invalid trust-boundary matrix names its violations and routes to the checklist answers. A task/validation contract conflict, a review-lane conflict, a changed contract approval or evidence Garda cannot inspect is marked as an operator decision. The blocked grouped follow-up audit is marked as an operator decision too. When the read-only reopen preview is the only command, the text output keeps the route's full reason and its one-line instruction instead of presenting the preview as the next action.
- A rejected declared validation is routed from Garda's typed errors and evidence facts only, never from its text, so a case id or path that spells a Garda diagnostic cannot turn an agent fix into an operator stop or a wrong run. A timeline, scope or recipe identity change during the validation inspection now offers a retry of `next-step` with a fresh inspection; the retry is bounded: it carries `--inspection-retry <attempt>:<content witness>`, and the same race on unchanged preflight and timeline content, or a fourth race in a row, becomes a marked operator decision. A preflight the recipes did not freeze offers the preflight refresh; a stable preflight equal to what the recipes froze is not a race and is reported to the operator instead of retried. A contract change after an already recorded audited admission offers the preflight refresh instead of an operator stop; any other approval change, and an unknown inspection error, stay operator decisions. Bound declared phases without a selectable execution say so instead of "could not inspect", and an operator decision on this step is no longer re-read from its text.
- The task-test selection that `next-step` offers (`workflow set --task-test-command ... --task-id ...`) is no longer refused when the installed workflow config holds an older optional quality-checks baseline than the shipped one (T-437). The selector counted the baseline version that Garda stamps by itself as a second requested setting. The selection writes only its own audit, so the live config and its baseline stay unchanged until an ordinary `workflow set` or update migrates them as before. A second setting the operator actually requests is still refused.
- An agent mistake in a post-review gate on the unchanged reviewed tree no longer forces a preflight refresh, an operator-confirmed `restart-coherent-cycle` or new reviews (T-437). When `doc-impact-gate` records a project-memory flag that the recorded `project-memory-impact` status contradicts, `next-step` routes back to `doc-impact-gate` with the corrected flag instead of `completion-gate`; the offered flag now follows the recorded status. After a completion failure the preflight stays current while the workspace still matches its scope fingerprints and the failed step is known (detected by `next-step` or already rerun by the agent); otherwise the previous refresh route stays. A reclassification that re-records the reviewed classification (same scope, content, criteria and required reviews) opens no new execution cycle: `next-step` reruns compile and the other preflight-bound evidence steps on it, re-binds each passed review through review reuse without a fresh reviewer, and completion keeps the reviewed cycle. Such reruns are bounded: when a completion failure repeats one an earlier identical reclassification already answered (compared with per-round sequences, hashes and timestamps masked), after at most two identical reclassifications of one reviewed classification, or when the full task history cannot be read, `next-step` stops with the cause named and offers a new review cycle only after the user approves it. The wrong records stay in the task timeline. A real code, scope, criteria or review-requirement change still takes the existing restart route.
- Remediation line evidence is stored only where it is safe and never where the previous release did not store it (T-437). Line hashes and redacted lines are now split on the same line feeds, and line evidence is kept only for text whose control characters are TAB, LF and CR before LF (or a final CR): any other C0 or C1 control, DEL, U+2028 or U+2029 gives no line evidence, and stored evidence with such a character is rejected on reload and rewritten by the serializer. When redaction changes the line structure (for example an `Authorization: Bearer|Basic` value split across a line break, or a multi-line secret value at the end of a file), the file still gets no line evidence, so remediation falls back to FULL review as before. A file whose line evidence is withheld is still charged to the snapshot line budget as the previous release charged it, so withholding evidence never gives a later file evidence the previous release did not give it. The persisted delta-base `line_analysis` names these cases `redaction_line_mismatch`, also used when whole-file and per-line redaction disagree, so stored line evidence always reloads under its own hash; `line_count_limit_exceeded` is reserved for files above the per-file line limit. A changed ordinary document with `redaction_line_mismatch` evidence now forces FULL review even beside code, and so does one whose recorded `line_count_limit_exceeded` the current file does not confirm; genuinely large documents stay exempt as before. Capture applies the same aggregate redacted-byte cap as validation: a file whose redacted lines would exceed it records `snapshot_line_budget_exceeded` instead of evidence that validation would reject. New delta bases carry `line_evidence_version: 2`. A remediation baseline recorded before this update has none, so the first fix measured against it repeats the review once in FULL instead of trusting its earlier line evidence; later fixes get DELTA again from the new baseline. Transition rule: the version is required only when Garda decides a new DELTA. A review mode decided, a review context built, a reviewer launched or a result recorded before the update completes as before, so an in-flight DELTA review is neither refused nor restarted, and reviews that already ran stay valid for reuse checks, lane carry-forward and the task audit; only a fix classified after the update against an unversioned baseline is reviewed once in FULL.

### More reliable reviews and recovery

- Review reuse no longer trusts a review context that an earlier `build-review-context` only saved after refusing reuse. A rebuilt context matches a passed review only through the reuse hash recorded in its receipt or through previous context bytes bound to that receipt. A changed task criterion always requires a new review, and on the hash-matching path so does a changed review depth or other review-context reuse input, however many times the context is built. Reuse after a test-only change or a scope preserved by a remediation decision, which tolerates a changed scope without a hash match, now also requires the review depth to be the reviewed depth or the depth the current classification prescribes (resolved as `next-step` resolves it); the reviewer source of truth cannot change within a task mode (the context build refuses the contradictory runtime identity), and task criteria and the rule, coverage and execution contracts are checked on every path. A refined agent description and an approved review-policy change still keep passed reviews.

- Grouped review findings now become one follow-up after completion passes, immediately before the final report lists the child. A failed completion leaves the deferred obligations in their authenticated review receipts. Garda verifies the complete canonical lane set under the queue lock and records publication against completion before final audit.

- A review that failed with findings to fix now sends the agent straight to the fix while the reviewed code is unchanged. Previously, recording such a failure could make the quality checklist look stale, and navigation then refreshed the checklist, rebuilt the review context and asked for a new reviewer of the same unfixed code. A task already in that state is routed to the fix too, as long as no new preflight, task-mode entry or review cycle restart has been recorded since the failed review. The checklist and review context are still refreshed after the fix, before the review runs again.
- Deferred findings from several review lanes now go into one grouped follow-up task in a single step. Navigation prescribes one `materialize-review-follow-up-tasks --review-types "<lane>,<lane>"` command for all lanes that still have deferred items. Previously, after a review cycle restart that reused some lanes and reviewed others again, adding the lanes one at a time could stop with an incomplete lane registry error. Rerunning the materialization for a grouped task that mixes reused and freshly reviewed lanes now reports it as already materialized. The same command is used for one remaining lane when the grouped follow-up task already exists. When the grouped command that navigation prescribes has been refused by grouped follow-up admission (its lane registry or review reuse check) and neither Garda's version nor any review evidence, task row or timeline entry it checks has changed, navigation stops repeating it. Other refusals and lock or write failures keep the command prescribed. A task already stuck with a grouped follow-up task that misses some lanes recovers through the operator-confirmed command that navigation prints: after the operator confirms that those lanes were never materialized, the command adds them to the existing follow-up task and records the recovery in the task timeline.
- A task with an empty diff needs no review or task test, even when `TASK.md` declares review lanes or the project has a matching domain surface. It closes through audited no-op evidence. Previously such a task asked for task tests that no selection could satisfy, before the review check and again at closeout. Explicit `--force-code-review` and `--force-all-domain-reviews` still keep reviews.
- A preflight refresh for a task with planned files no longer adds an unchanged file that another active task left in the worktree.
- Rebuilding lost preflight or passing validation evidence for the same files now keeps passed reviews when the original evidence can be verified.
- A file changed after the required reviews passed no longer starts a new review cycle automatically. Navigation names the files and asks the agent to revert the change and continue closing, or to tell the user when the change is truly necessary. The restart then runs a new review cycle only with the user's approval (`--review-restart-approved yes` and an approval time no older than ten minutes), records that approval, and refuses without it. The approved cycle follows the same rules as a change made before the reviews passed: a review the change does not reach keeps its result, a small fix inside a review's scope repeats it delta-only, and documents repeat nothing. If the change cannot be authenticated or classified against the reviewed files, for example because its baseline is missing or a protected trigger is invalid, every required review repeats in full. Recovery of lost evidence with an unchanged workspace needs no approval. A review whose receipt or report is deleted or damaged after the reviews passed now repeats, as it does before; previously the restart quietly brought its old result back.
- Missing or corrupt reviewer launch controls now name operator recovery, and lost prompt inputs name the applicable context or failed-launch recovery. Timing, immutable-launch and invalid findings refusals retain their checks and give concrete guidance. Required-review lifecycle refusals retain their recovery instruction even when diagnostic output is truncated.
- Remediation keeps passed reviews outside the fix in all four execution modes, including the test review. A profile dependency graph can reopen downstream reviews, including dependencies of lanes reached by the fix. In the default `strict_sequential` mode, launch order alone no longer reopens later reviews: a shared test helper fix repeats refactor and test while keeping code and security. Preserved proofs survive a full-suite context refresh and validated links survive an unusable older restart.

Owned configuration asks FULL of its owner, while project instruction files repeat code and test in DELTA for a small fix. Default helper folders no longer hide production source outside common source roots, and source-root test helpers no longer repeat code review.
