# Adding a field regression

Every defect found outside the stand gets a permanent `field-вЂ¦` scenario, even when an existing synthetic family appears similar. Keep its source task/incident ID and the distinguishing conditions in the scenario description.

1. Add its ordinary project inputs under `tests/fixtures/stacks/` or derive a fixture in `engine/walk-field-cases.ts`. Preserve the real project shape, command argv, previous selection and failure conditions. Fake only the toolchain; execute the real navigator and public native commands.
2. Add the ID to `FIELD_CASE_IDS`, `FIELD_CASE_SCENARIOS` and the `field-cases` check in `stand-properties.json` for both full and sweep. Add a property/check mapping for any new error class. Meta-tests must reject an omitted scenario; never declare a product dead end as an expected handoff.
3. Supply an independent `inspectResult` assertion for the defect, required routes, DONE and exact review counts/modes. Observe offered commands with `inspectNavigation` before the synthetic agent chooses or substitutes anything. Test meaningful negative controls: removing a target, changing argv or suppressing the offered recovery must fail.
4. Produce gate evidence through native commands. For migration, build an immutable older revision with the existing dependencies and run its actual commands in the disposable project. Preserve old timeline/artifact bytes; do not manufacture old receipts, rewrite FAILED to PASS or backdate events.
5. Run the field family with `GARDA_SYNTHETIC_WALK_ONLY` set to its comma-separated IDs, `GARDA_SYNTHETIC_WALK_LEVEL=full`, seed `1785881697`, provider `Codex`, and `GARDA_SYNTHETIC_WALK_JOBS=3`. Keep the native report and scenario ID when a product defect remains. Fix product code in its owning worktree.
6. Record deliberate expectation-source changes through `stand.cjs baseline --kind expectations --candidate current` with a concrete written reason. Review counts/modes and all old work budgets remain binding. Do not calibrate away a field failure.

The active cases cover the misleading in-scope refusal, the missing own-test reselection offer for a project-command selection, `.cmd` CALL argv distortion, and OP-035 historical failure attribution. The Windows case checks argv observed by the child process; execution on a different OS does not certify Windows shell behavior.

Synthetic runners do not certify Maven, Java, shell behavior on another OS or a real agent's choices. External acceptance uses manually authorized three-OS CI, T-406/T-408 and real projects.

OP-035 (`field-onlinestore-op035-follow-up-attribution`) runs the pinned older native producer against Maven-shaped timestamps and exception diagnostics. The new reader retains the original authenticated failure/attribution unchanged, materializes an unattributed grouped follow-up without false test names, narrows to both own modules and reaches DONE with the original review counts/modes. The native command regression separately checks repair of an already generated legacy row, idempotence and preservation of edited operator text.

The two-module Spring field shape uses `stack-fixture-spring-maven-two-modules`, inheriting the original single-module profile. Independent one/two-module native controls and unchanged-input five-event controls are retained in `field-spring-two-module-calibration.json`. Eight additional authenticated directories explain 16 realpath probes; the two additional changed source/test files explain two hashes. Every old profile, Git/ACL ceiling and history-growth limit stays unchanged. Historical producer archives are separated by scenario ID.

## 1.4.4 final-review cases

The `field-r144-*` walks (`engine/walk-field-r144-scenarios.ts`) keep the defects the final 1.4.4 review found while the stand was green. Each has an independent oracle derived from the concept rules, not from product output:

- `field-r144-lane-enable-keeps-passed-reviews`, `-lane-disable-keeps-passed-reviews`, `-lane-enable-with-criteria-change` (R2-2, C6.2.4): the operator changes the API capability through `review-capabilities` for an unchanged API scope; passed code/test reviews are kept and a newly enabled lane runs once FULL; a criteria change in the same moment reruns every required lane FULL.
- Not registered (known gap): `field-r144-criteria-change-double-context` and `-criteria-change-double-context-operator-intent` (R2-1/T-468; the public CLI refuses the second context build with REVIEW_CONTEXT_REFUSED before reuse is evaluated, so the walk cannot prove the defect; the fix in 85ca862f is covered by product tests, `fix-intent2.stand-request.md`, C6.1.3/C6.1.4/C6.2.4): after the first code PASS, change only the TASK.md title requirement or explicitly confirmed operator intent. Build the identical new code context twice before any new reviewer. Neither build may materialize old PASS authority. Original snapshots and unchanged sources/scope are checked; the contract is `code:FULL, code:FULL, test:FULL`.
- `field-r144-protected-restart-keeps-criteria` and `-protected-restart-after-agent-supplement` (`fix144-protected.report.md`, C6.2.1/C6.2.4): after code/test PASS in an operator-approved orchestrator task, remove handshake and compile evidence and execute the navigator's coherent restart with its protected re-entry confirmation. There must be no operator-intent event or criteria-digest change; both original PASS artifacts are reused and there are only the original `code:FULL, test:FULL` launches. The second case first records an agent supplement through `restart-review-cycle`.
- `field-r144-protected-restart-operator-criteria-change` and `-protected-restart-confirms-agent-supplement` are authority controls: explicitly stating new operator intent through the coherent restart (including exactly the earlier agent wording) creates one operator-intent event and repeats both mandatory lanes FULL, giving `code:FULL, test:FULL, code:FULL, test:FULL`. These distinguish actual intent authority from protected re-entry confirmation.
- In every `field-r144-*` walk the modeled reviewer runs the required read-only `record-review-result --check-only` self-check printed in its launch handoff (`reviewerSelfCheck`) and it must accept a contract-valid report without changing runtime state. Before this, no walk executed that mandatory reviewer step.
- Not registered yet (2.0): `field-r144-legacy-prefix-continue` and `-legacy-prefix-forged-launch` (R3-2, `R144_KNOWN_GAP_IDS`). A timeline whose chain starts after an unsigned pre-integrity event must reach DONE with passing self-checks, and a launch found only in the unsigned prefix must be refused. Both stop earlier, at task-test selection, on the known T-469 item 3 (strict PASS history checks); register them when T-469 lands.
- `field-r144-omitted-required-lane-refresh` (R1-1, C2.4): a lane added to the task notes after preflight must be offered as an executable refresh on the very next navigation.
- `field-r144-unavailable-required-lane` and `-disabled-required-lane-after-selection` (R1-1 round 2): an unavailable declared lane is an operator authority decision. Two consecutive navigations return the same commandless refusal naming the lane and change nothing; after the modeled operator enables the lane, the task reaches DONE.
- `field-r144-red-changed-declared-fixture` (R1-2, C5.1.1): an unknown-stack TDD task changes its test and the declared fixture; one RED of the test covers the fixture.
- `field-r144-failed-task-local-compile-retry` (R1-3, C2.4, C4.2): after a real task-local compile failure with no project command, every command the navigator offers is executed and must be accepted by its handler; the stored command is actually rerun.
